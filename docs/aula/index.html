Parte I — A fundação (a infraestrutura que sustenta a loja)

F1Docker — mini máquinas virtuais na sua máquina

Imagine vários computadores separados rodando ao mesmo tempo DENTRO do seu computador — cada um com seus arquivos e programas, todos ligados por uma rede. É isso que o Docker cria.

flowchart TB subgraph HOST["SEU COMPUTADOR (host)"] subgraph NET["REDE DOCKER — todos se enxergam pelo nome"] C1["container:
catalog :5000"] C2["container:
order :5000"] C3["container:
postgres :5432"] C4["container:
rabbitmq :5672"] C5["container:
grafana :3000"] end end C1 ---|"HTTP: http://catalog:5000"| C2 C2 --- C3 C2 --- C4

Cada container é uma mini máquina virtual com endereço de rede próprio. No código, o "nome do computador" vira URL — é por isso que o order chama http://catalog:5000.

Mini máquinas virtuais

Cada container tem seus próprios arquivos e processos, como um computador separado. Se um "queima" (bug, crash), os outros continuam rodando normalmente.

O Docker é o administrador

É ele quem cria as mini-máquinas (docker run), liga e desliga, e conecta todas na mesma rede. Sem Docker, você instalaria cada serviço "à mão" na sua máquina — versões conflitando, bagunça.

Imagem = receita, container = máquina ligada

A imagem é a receita (arquivos + instruções congeladas). O container é a mini-máquina criada a partir dela, rodando. Uma imagem pode gerar várias máquinas idênticas.

O problema que mata

"Na minha máquina funciona." Cada serviço depende de versões de Python, bibliotecas, variáveis... Com Docker, o ambiente viaja junto com o código: roda igual em qualquer máquina.

services/catalog/Dockerfile — a receita do serviço de catálogo 
FROM python:3.10                     # base: Python já instalado
WORKDIR /app
COPY shared/ /app/shared/           # a biblioteca comum entra na imagem
COPY services/catalog/ /app/       # o código do serviço
RUN pip install --no-cache-dir /app/shared && pip install --no-cache-dir -r requirements.txt
ENV PYTHONPATH=/app:/app/shared
EXPOSE 5000
CMD ["python", "app.py"]      # o que roda quando o container sobe
# na prática 
docker build -t catalog .          # constrói a imagem
docker run -p 5000:5000 catalog   # sobe UM container

F2Docker Compose — a planta da loja inteira

No capítulo anterior, o Docker criava UMA mini máquina por vez (docker run). E quando a loja tem 12 máquinas? Digitar 12 comandos, na ordem certa, conectando uma na outra... É aí que entra o Docker Compose: você escreve num arquivo como a loja inteira deve ficar — e ele liga tudo de uma vez.

docker-compose.yml — a planta: todas as mini máquinas declaradas 
services:                               # cada item = uma mini máquina a ser ligada
  postgres:  image: postgres:15-alpine
  rabbitmq:  image: rabbitmq:3-management-alpine
  grafana:   image: grafana/grafana:11.0.0

  catalog:                              # os nossos serviços (têm Dockerfile próprio)
    build: { context: ., dockerfile: services/catalog/Dockerfile }
    depends_on:
      postgres: { condition: service_healthy }   # "só ligue depois que o banco estiver pronto"
    environment:
      POSTGRES_DB: catalog_db
# na prática 
docker compose up -d --build   # lê a planta e liga TODAS as mini-máquinas de uma vez
docker compose ps              # lista as máquinas ligadas e o estado de cada uma
docker compose logs -f order   # segue a "tela" de UMA máquina (o serviço order)
docker compose down -v         # desliga tudo e apaga os dados (voltar ao zero)

A planta da loja

O docker-compose.yml descreve todas as mini-máquinas: qual receita (imagem) cada uma usa, portas, senhas, variáveis. Lendo o arquivo, você entende a loja inteira — é a documentação viva da infraestrutura.

Ligar na ordem certa

depends_on com service_healthy é o checklist de inicialização: "só ligue o catálogo depois que o banco disser estou pronto". O healthcheck é a pergunta "a máquina já está de pé?" que o Compose faz antes de ligar a próxima.

Rede pronta

Todas as mini-máquinas nascem conectadas na mesma rede do capítulo anterior. Nenhum IP configurado à mão: o nome do serviço vira endereço — por isso o código chama http://catalog:5000.

Sobe tudo num comando

Clonou o repositório? docker compose up -d. A loja inteira (bancos, filas, dashboards, serviços) nasce idêntica em qualquer máquina. Zero configuração manual.

Na nossa lojaorder, payment, invoice — o dinheirocatalog (DocumentDB) e cart (Redis) seriam ótimos

Dinheiro e estoque não podem errar

Transação ACID = tudo ou nada. Pedido, pagamento e o evento do outbox (capítulo 05) nascem no MESMO commit — ou todos juntos, ou nenhum. É isso que sustenta a loja.

Dados interligados

Pedido → itens → produtos → NF → entrega: no SQL, uma consulta com JOIN monta a história inteira. No NoSQL, você remontaria essas relações no código da aplicação.

Catálogo e carrinho? NoSQL seria até melhor

O catálogo é leitura pesada com atributos variados — um DocumentDB encaixa perfeitamente (ainda mais depois de separar o estoque no inventory). O carrinho é efêmero e quente — Redis com TTL. Mantivemos tudo em Postgres só para o exemplo da aula ficar simples.

Parte II — A Jornada do Pedido (os padrões da loja)

00Por que microsserviços?

Antes da jornada: a loja era um sistema único — o monólito.

flowchart LR subgraph Mono["Monólito — uma aplicação"] A["Tudo junto:
catálogo, carrinho, pedidos,
pagamento, estoque..."] B[(1 banco)] end A --> B

O problema

Um pico em "pagamentos" exige escalar a loja inteira. Um bug no carrinho derruba o catálogo. Todo deploy move tudo — e todos os times ao mesmo tempo.

A aposta

Dividir a loja em serviços independentes: cada um com seu código, seu banco e seu ciclo de deploy. O preço: comunicação em rede, mais falhas possíveis — e novos padrões para domá-las.

Fonte: microservices.io — cada serviço tem seu próprio banco de dados.

01API Gateway — o porteiro da loja

O cliente não conhece os serviços. Ele fala com UM endereço: :8080.

flowchart LR C["Cliente / Postman"] --> G["Nginx Gateway :8080"] G -->|/api/v1/catalogo/*| CAT[catalog] G -->|/api/v1/carrinho/*| CART[cart] G -->|/api/v1/pedidos/*| ORD[order] G -->|/api/v1/pagamentos/*| PAY[payment]
config/nginx/nginx.conf 
# Rate limit global da API: 10 requisições/s (burst de 20)
limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;

# O RG do pedido: gerado na porta da loja e devolvido em toda resposta
add_header X-Correlation-ID $request_id always;

# Roteia por caminho: /pedidos → serviço "order"
location ~ ^/api/v1/pedidos/(.*)$ {
    set $backend order;
    limit_req zone=api burst=20 nodelay;
    proxy_pass http://$backend:5000/$1$is_args$args;
    proxy_set_header X-Correlation-ID $request_id;
}

O que acontece aqui

Roteamento por caminho, rate limit, e o carimbo de entrada: o X-Correlation-ID — gerado na porta e carregado por toda a jornada.

Por que importa

Serviços internos mudam sem o cliente perceber. Segurança e política num ponto só. E o correlation ID vira a "cola" que rastreia o pedido do início ao fim.

A regra de ouro

Se um serviço precisa de dados de outro, ele pede via API ou evento — nunca via banco. Acoplamento de banco é a receita do "monólito distribuído".

03Comunicação síncrona — e o disjuntor (Circuit Breaker)

Quando o pedido precisa da resposta AGORA (preço, estoque), a chamada é direta. E direta pode falhar.

flowchart LR ORD[order] -->|"GET /carts/:id"| CART[cart] ORD -->|"POST reserve"| CAT[catalog] ORD -->|"POST /payments"| PAY[payment] CART -->|"GET /products/:id"| CAT
shared/lab_common/http_client.py — o disjuntor, por serviço de destino 
def _breaker_for(self, url, fail_max, reset_timeout):
    host = urlparse(url).netloc          # ex.: "payment:5000"
    if host not in self._breakers:
        self._breakers[host] = pybreaker.CircuitBreaker(
            fail_max=3,          # 3 falhas seguidas → circuito ABRE
            reset_timeout=30,    # 30s de folga, depois testa 1 chamada
            name=f"http:{host}",
        )
    return self._breakers[host]
shared/lab_common/http_client.py — a chamada protegida 
@breaker
def _do():
    headers = {}
    propagate.inject(headers)            # W3C Trace Context (traceparent)
    cid = get_correlation_id()
    if cid:
        headers['X-Correlation-ID'] = cid   # o RG do pedido viaja junto
    r = requests.request(method, url, json=json, timeout=2, headers=headers)
    if r.status_code >= 500:
        raise Exception(f"HTTP {r.status_code}")   # conta como falha
    return r

Fonte: martinfowler.com — fechado (normal) → aberto (falha rápida) → meio-aberto (testando).

O disjuntor

Depois de 3 falhas seguidas num destino, o circuito ABRE: as próximas chamadas falham na hora (503), sem esperar timeout. A cada 30s, uma chamada de teste passa — se funcionar, fecha de novo.

Por que importa

Sem disjuntor, um serviço lento derruba o outro — e a lentidão vira efeito dominó em toda a loja (o "cascading failure").

04Comunicação assíncrona — os motoboys (eventos)

Nem tudo precisa de resposta imediata. Emitir NF, agendar entrega, registrar garantia... acontecem DEPOIS.

topic orders.events} RMQ -->|order.paid| INV[invoice-worker] RMQ -->|order.paid| LOG[logistics-worker] RMQ -->|order.paid| WAR[warranty-worker]
services/order/app.py — "pedido pago" vira evento no outbox 
o.status = 'PAID'
_append_outbox(s, order_id, 'order.paid', 'order.paid',
    {'orderId': order_id, 'total': total, 'items': items, ...})
services/invoice/worker.py — quem se importa, assina o tópico 
rabbitmq_service.declare_topic_exchange('orders.events', [
    {'name': 'invoice.order_paid', 'routing_keys': ['order.paid'], ...}
])
run_worker('invoice', 'invoice.order_paid', handler, ...)

Padrão

O order publica um EVENTO ("pedido foi pago!") e volta ao trabalho. Quem se importa, assina o tópico. Ninguém espera ninguém.

Por que importa

Desacopla: um novo serviço (e-mail, por exemplo) entra só assinando o tópico — sem tocar no order. E o pico de um não contamina o outro.

05Outbox — a promessa de entrega

O pesadelo: o pedido salva no banco, mas o evento se perde no caminho. Como garantir que os dois acontecem JUNTOS?

flowchart LR subgraph TX["MESMA transação no order_db"] O[Pedido PAID] --> OUT[("tabela outbox:
evento não publicado")] end OUT --> R[relay a cada 1s] R -->|publica| RMQ{RabbitMQ} R -->|"✔ marca published"| OUT
services/order/models.py — a tabela que guarda a promessa 
class OutboxEvent(Base):
    __tablename__ = 'outbox_events'
    ...
    payload = Column(Text, nullable=False)
    published = Column(Boolean, default=False, index=True)
    published_at = Column(DateTime, nullable=True)
services/order/app.py — gravar juntos; publicar depois 
# 1. O evento é gravado NA MESMA transação do pedido (tudo ou nada)
o.status = 'PAID'
_append_outbox(s, order_id, 'order.paid', 'order.paid', {...})
s.commit()   # pedido + evento: os dois commitam, ou nenhum

# 2. O relay (thread em background) entrega depois, a cada 1s:
pending = s.query(OutboxEvent).filter(OutboxEvent.published == False)...
for ev in pending:
    rabbitmq_service.publish(payload, correlation_id=..., exchange='orders.events')
    ev.published = True   # só marca depois que o broker confirmou

A sacada

O evento NÃO vai direto ao broker. Ele é gravado numa tabela outbox na mesma transação do pedido — os dois commitam ou os dois caem. Depois, um relay entrega com retry até o broker confirmar.

Garantia

At-least-once: o evento nunca se perde; no pior caso chega duas vezes. E é aí que entra a idempotência...

06Saga e compensação — o estorno

E se o pagamento falhar no meio do caminho? Alguém precisa desfazer o que já foi feito.

flowchart TD A[1. Reserva estoque] --> B[2. Cobra pagamento] B -->|aprovado| C[3. Publica order.paid] B -->|recusado| D[4. Compensa: devolve estoque +
publica order.rejected] D --> E[workers cancelam logística/garantia]
services/order/app.py — reserva com compensação imediata 
def _reserve_stock(items):
    reserved = []
    for it in items:
        try:
            hc.call(f'{CATALOG_URL}/products/{pid}/reserve', method='POST', ...)
            reserved.append((pid, qty))
        except Exception as e:
            # falhou no meio → DESFAZ o que já tinha reservado
            for (rpid, rqty) in reserved:
                hc.call(f'{CATALOG_URL}/products/{rpid}/release', method='POST', ...)
            raise
services/order/app.py — pagamento recusado: compensa + evento no MESMO commit 
o.status = 'REJECTED'
_release_stock(items)                    # devolve o estoque (compensação)
_append_outbox(s, order_id, 'order.rejected', 'order.rejected',
    {'orderId': order_id, 'status': 'REJECTED', ...})
s.commit()  # rejeição + evento: atômicos — o aviso aos workers nunca se perde

Saga

Uma transação longa, distribuída, executada em passos por serviços diferentes — com uma história para cada desfecho.

Compensação

Não dá pra dar "rollback" em outro banco. Então cada passo tem seu inverso: reservou estoque → devolve. Emitiu NF de pedido pago → só se foi pago mesmo. O evento order.rejected avisa os workers.

07Idempotência — nada acontece duas vezes

Retries existem. Rede falha. Mensagens chegam de novo. A loja precisa sobreviver a isso.

services/invoice/worker.py — NF nunca é emitida duas vezes 
def handler(data, correlation_id, span):
    order_id = data.get('orderId')
    # Idempotência durável: se já existe NF deste pedido, não faz nada
    if s.query(Invoice).filter(Invoice.order_id == order_id).first():
        return
    inv = Invoice(invoice_id=str(uuid.uuid4()), order_id=order_id, total=total)
    s.add(inv); s.commit()
shared/lab_common/worker.py — primeira barreira: o correlationId 
if correlation_id in processed_cache:
    logger.warning("Idempotency: duplicate dropped.", extra={...})
    ch.basic_ack(delivery_tag=method.delivery_tag)   # reconhece e descarta
    return

A regra

Toda operação de "efeito" precisa poder rodar 2x com o mesmo resultado: checar antes de inserir, usar IDs de negócio (correlationId/orderId) como chave.

No lab

Workers conferem correlationId antes de processar; o invoice só emite NF se não existir uma para aquele order_id (constraint UNIQUE + upsert).

class OtelContextFilter(logging.Filter):
    def filter(self, record):
        span = trace.get_current_span()
        record.traceId = format(ctx.trace_id, "032x")   # técnico (W3C)
        record.spanId = format(ctx.span_id, "016x")
        record.correlationId = get_correlation_id()       # negócio (gateway)
        return True

Os três pilares

Logs (Loki): o que aconteceu. Métricas (Prometheus): quantos/quão rápido. Traces (Tempo): o caminho completo do pedido, span a span.

Os dois fios condutores

traceId (técnico, W3C Trace Context) e correlationId (negócio): com qualquer um, você acha TODOS os registros de um pedido — do gateway aos workers.

10Grafana & Prometheus — as ferramentas por dentro

Você já viu o que os 3 pilares capturam (capítulo 09). Agora o COMO: Grafana e Prometheus estão instalados e provisionados na loja desde a primeira subida.

Cada serviço expõe /metrics (contadores de requests, pedidos, erros...). O Prometheus "raspa" (scrape) a cada 5s e guarda a série temporal.

Grafana (a vitrine)

Lê Prometheus, Loki e Tempo. Dashboards e datasources já vêm provisionados: sobe a stack e os gráficos estão lá.
